# Probe sweep — 1,041 labelled queries across 52 buckets (run 29b model)

First full run of the probe loop. **No retraining involved** — this scores the
already-exported model. Total wall time ~25 min, almost all of it generation.

```
intent accuracy   83.8%
intent+taskType   72.3%
```

**Read §1 before quoting either number.**

---

## 1. The probe set has label noise — the bucket figure is a floor, not a fact

The "label by construction" guarantee holds only if the LLM actually obeys the
target taskType. It does not always. Clearest case:

**`SIP_VS_PREPAY|SUMMARY` scored 0/20 — and the model was right, not wrong.**
- intent accuracy on that bucket: **100%**
- every probe generated was comparison-shaped: *"2 lakh bacha hai, SIP karun ya
  loan prepay?"*, *"3k monthly invest karu ya 4 lakh loan 8% prepay?"*
- model predicted COMPARISON (15) / WHAT_IF (5) — the correct reading

The prompt *did* list COMPARISON and WHAT_IF as must-avoid siblings. The model
ignored it because SIP_VS_PREPAY|SUMMARY is close to unphrasable without
comparing — the intent **is** a comparison. That is itself a finding: this
bucket may not deserve to exist (see §4).

`SAVINGS_ADVICE|SUMMARY` (30%) has the same defect — probes like *"budget karo
3k month wise savings plan 12 months"* are genuinely GOAL_PLANNING.

**Consequence:** treat 72.3% as a lower bound. Where intent accuracy is high but
bucket accuracy is low, suspect the label before the model.

## 2. What IS trustworthy: intent-level confusions

These do not depend on taskType labelling, so they survive §1.

| n | confusion | reading |
|---|---|---|
| 12 | ADD_INCOME → ADD_EXPENSE | **money-in vs money-out** on write intents |
| 10 | SAVINGS_ADVICE → GOAL_PLANNING | saving-for vs saving-generally |
| 8 | DEBT_FREEDOM → ADD_LIABILITY | asking about debt vs recording one |
| 8 | FAMILY_TRANSFER → ADD_INCOME | direction of a person-to-person transfer |
| 7 | LOAN_ANALYSIS → DEBT_FREEDOM | the boundary "fixed" in iteration 17 |
| 6 | DEBT_FREEDOM → AFFORDABILITY_CHECK | |
| 5 | SPENDING_ANALYSIS → INCOME_ANALYSIS | |

### 2.1 The standout: ADD_INCOME → ADD_EXPENSE (21 misroutes total)
```
"add 7500 from zara store"        -> ADD_EXPENSE
"4000 cr from client"             -> ADD_EXPENSE
"actually i got 4500 HDFC 03-20"  -> ADD_EXPENSE
"change 05-05 credit to 5k"       -> ADD_EXPENSE
```
The word **"from"** appears in both *"spent 500 **from** my card"* and
*"got 7500 **from** Zara"*, and a merchant name pulls hard toward expense. The
model is keying on merchant presence rather than the direction verb
(got/received/credited vs spent/paid).

This is the highest-value single fix on the board: it is a **write** intent, the
highest-traffic real-world path, and getting it wrong writes a transaction with
the wrong sign.

### 2.2 A cluster worth noticing
ADD_INCOME→ADD_EXPENSE, FAMILY_TRANSFER→ADD_INCOME, DEBT_FREEDOM→ADD_LIABILITY,
ADD_ASSET→ADD_LIABILITY are all **direction/ownership** confusions, not topic
confusions. The model knows the domain; it does not reliably know which way the
money is moving. That suggests one targeted pattern family (explicit
direction-verb contrast) rather than four separate fixes.

## 3. taskType-only weaknesses (intent right, task wrong)

Where intent accuracy is high but bucket accuracy is low — after discounting
§1 label noise:

| bucket | bucket / intent | note |
|---|---|---|
| DEBT_FREEDOM_ANALYSIS\|SCHEDULE | 35% / **95%** | schedule vs summary unresolved |
| INCOME_ANALYSIS\|SUMMARY | 65% / **100%** | pure taskType split |
| INCOME_DECLARATION\|UPDATE | 65% / **100%** | update vs create |
| SPENDING_ANALYSIS\|ANALYSIS | 35% / 50% | the long-standing ANALYSIS cue gap |

`SPENDING_ANALYSIS|ANALYSIS` at 35% independently reconfirms the run-1 finding
that "Analyze"/"analysis" does not reach the ANALYSIS taskType.

## 4. Product questions this raises

1. **Should `SIP_VS_PREPAY|SUMMARY` exist?** An LLM explicitly told to avoid
   COMPARISON could not write 20 non-comparison queries for it. If the intent is
   inherently comparative, SUMMARY may be a bucket we are training the model to
   fail at.
2. **Hinglish** — still unresolved from the isolated run, and now visible inside
   the probe set too.

---

## 5. Tooling defect found and fixed during this sweep

The first sweep lost **25 of 55 buckets (45%)** to truncated JSON:
`num_predict: 2048` cut responses mid-array at count=20, and the parser
discarded the whole batch for a missing closing bracket. Every one of those
buckets had produced good queries.

Dangerous property: a generator silently discarding half its output looks
identical to one whose model refused the task. Fixed two ways —
- salvage stage extracts complete quoted strings from truncated arrays
- cap raised 2048 → 8192

Re-ran only the 25 failed buckets: **24 recovered, 0 failures**.

## 6. Priority

1. **Direction confusion cluster** (§2.1/§2.2) — one pattern family, fixes the
   highest-traffic write path. Biggest genuine win.
2. **SPENDING_ANALYSIS|ANALYSIS** cue gap (§3) — third independent sighting.
3. **DEBT_FREEDOM SCHEDULE/STRATEGY** taskType boundaries (§3).
4. **Probe-set hygiene** — add a self-check pass: re-ask the LLM to label its
   own generated queries blind, and drop any where the returned label disagrees
   with the requested bucket. That would remove most of §1's noise.
5. Product calls: SIP_VS_PREPAY|SUMMARY existence, Hinglish.
