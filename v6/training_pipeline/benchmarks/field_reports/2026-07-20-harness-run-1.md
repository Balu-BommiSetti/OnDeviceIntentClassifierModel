# Field report — harness run 1 (2026-07-20, run 29b model)

First real-device harness run, 40 queries, generated by an external LLM.
Model: run 29b, vocab 2689, paired, on-device path confirmed active.

**Read this before acting on the numbers.** The headline "36/40 SPENDING_ANALYSIS"
is not a model result — it is a property of the *test set*. See §1.

---

## 1. The suite tests ~5% of the product

| | |
|---|---|
| intents in the taxonomy | 19 |
| intents this suite intends to cover | **1** (SPENDING_ANALYSIS) |
| intents touched at all | 5 — and 4 of those only by *misclassification* |
| taskTypes in the taxonomy | 15 |
| taskTypes exercised | **3** (SUMMARY, INSIGHTS, ANALYSIS) |

Never tested, not even once: every write intent (ADD_EXPENSE, ADD_INCOME,
ADD_ASSET, ADD_LIABILITY, REFUND, FAMILY_TRANSFER, INCOME_DECLARATION), every
debt/loan intent (LOAN_ANALYSIS, DEBT_FREEDOM_ANALYSIS, SIP_VS_PREPAY),
BUDGET_PLANNING, GOAL_PLANNING, AFFORDABILITY_CHECK, NET_WORTH_CHECK. And
COMPARISON / TREND / WHAT_IF / STRATEGY / SCHEDULE / RISK / STATUS /
ALLOCATION / CREATE / UPDATE / DELETE were never produced.

**Consequence:** this run cannot tell us whether the model is good. It tells us
one narrow slice is mostly working and surfaces a set of real bugs inside that
slice. The corrective action is a better *generation prompt*, which is the
separate deliverable.

---

## 2. Highest-severity finding: silent wrong-period answers

**PERIOD is dropped from the span, and the app then silently substitutes
TODAY.** The user gets a confident, well-formatted answer covering the wrong
time range, with nothing indicating the period was ignored.

| # | query | period asked | period used |
|---|---|---|---|
| 23 | "Show me my spending at Amazon **last month**" | last month | **today** |
| 29 | "What's my top spend category **this month**" | this month | **today** |
| 31 | "How much did I drop on gas stations **in July**" | July | **today** |
| 36 | "How much have I spent on water bill **this month**" | this month | **today** |
| 40 | "…the total amount I dropped on Flipkart **last month**" | last month | **today** |

That is **5 of 40 (12.5%)** answering about the wrong period. Every one is
higher-severity than a misclassified intent, because a wrong intent usually
produces a visibly odd answer, while a wrong period produces a plausible one.

Note the pattern in 23 and 40: PERIOD is dropped **when it follows a
MERCHANT**. Cases 24 and 32 (merchant + period) *did* extract the period, so
it is not absolute — but merchant-then-period is clearly the weak shape.

**Not yet verified:** whether the today-substitution happens in the extractor
or the mapping layer. Must be traced before fixing.

## 3. Confirmed model defects

### 3.1 Entity span swallowing (case 10)
`"Tell me how much I spent on Uber yesterday."`
→ span `{"date": "uber yesterday"}`

MERCHANT was absorbed into the DATE span. Merchant is then lost entirely —
the query would report *all* spending yesterday rather than Uber's. Wrong
answer, delivered confidently. Same failure family as the span-boundary work
in runs 15–16, so this shape needs a regression case.

### 3.2 Informal spend verbs not learned
"blow on" (18), "drop on" (31) — both slang for spending.
- 18 → INCOME_ANALYSIS @ 0.67 (spending question routed to income)
- 31 → UNKNOWN @ 0.00 (total failure)

Case 40 used "dropped on Flipkart" and *worked* (0.80), so the verb alone
isn't fatal — it compounds with an unfamiliar category (§3.3).

### 3.3 Category synonym gaps — the categories DO exist in the app
These failed on vocabulary, not capability. All three have valid app
categories the model never connected them to:

| query term | app category that exists | result |
|---|---|---|
| "gas stations" (31) | **Fuel** | UNKNOWN @ 0.00 |
| "Wifi" (37) | **Internet / Broadband** | not extracted |
| "coffee" (18) | **Tea & Coffee**, **Coffee Shop** | not extracted |

This is a *training-data* gap, cheap to close, and worth doing before any
architectural work.

### 3.4 Confidently wrong intents
| # | query | got | should be |
|---|---|---|---|
| 11 | "Show me the category breakdown for this year." | SAVINGS_ADVICE **@ 0.96** | SPENDING_ANALYSIS |
| 20 | "Where did my money go last year?" | CASHFLOW_WARNING **@ 0.89** | SPENDING_ANALYSIS |
| 18 | "How much did I blow on coffee this month?" | INCOME_ANALYSIS @ 0.67 | SPENDING_ANALYSIS |

High confidence on wrong answers is worse than low confidence — the 0.50 floor
cannot catch these. 11 and 20 are both *category-breakdown* questions, which is
squarely SPENDING_ANALYSIS territory.

### 3.5 Category hallucination (case 11)
`"Show me the category breakdown for this year."` → mapped `category: "Clothing"`.
Nothing in the query mentions clothing. A fabricated filter silently narrows
the answer to one category. Source is the merchant/category classifier, not the
NER head — needs tracing.

### 3.6 "Analyze" does not map to ANALYSIS
| # | query | taskType | conf |
|---|---|---|---|
| 14 | "**Analyze** my expenses for the last 90 days." | INSIGHTS | 0.43 |
| 25 | "**Analyze** my spend on groceries for Q1." | SUMMARY | 0.33 |
| 35 | "Give me an **analysis** of my total spend for Q4." | SUMMARY | **1.00** |

The most explicit possible ANALYSIS cue, and it lands on ANALYSIS zero times
out of three. Case 35 is confidently wrong.

### 3.7 Identical question shape → different taskType
- 29: "What's my top spend category **this month**?" → INSIGHTS @ 0.49
- 39: "What was my top spend category **in Q3**?" → ANALYSIS @ 0.50

Same question, two answers, both at coin-flip confidence. The
SUMMARY/INSIGHTS/ANALYSIS boundary is genuinely unresolved here — and this is
the same boundary flagged in the backlog as "debatable". It needs a product
decision, not more training data.

### 3.8 Trailing punctuation contaminates spans
Cases 16 (`"august 2022."`), 25 (`"q1."`), 35 (`"q4."`) — the full stop is
inside the PERIOD span and survives into the mapped value. Clearly wrong at the
span level. **Downstream impact unverified** — `parseResolvedMonth` may absorb
it via substring matching; must be tested before claiming breakage.

## 4. What looks broken but is fine

- **Truncated period spans** ("month", "year", "last") in cases 3, 4, 17, 21,
  24, 30, 33, 38 — the raw span drops the determiner, but the mapping layer
  reconstructs the correct value ("this month", "last year"). Cosmetic at the
  span level, correct at the product level. **Exception: case 12** ("last")
  was *not* reconstructed and stayed broken — so the compensation is not
  universal and should not be relied on.
- **"shopping" → Clothing** (case 9) — a defensible category mapping choice,
  not an error.

---

## 5. What this run does not tell us

- Nothing about write intents (logging expenses/income) — the highest-traffic
  real-world path.
- Nothing about multi-entity or comparison queries.
- Nothing about the debt/loan/goal advisory surface.
- Latency looks fine (202 ms avg) but was measured on one device, warm.

---

## 6. Suggested priority when we act

1. **Silent wrong-period substitution** (§2) — correctness bug, 12.5% of run,
   invisible to the user. Trace the today-fallback first.
2. **Category synonym gaps** (§3.3) — cheap training-data fix, closes 3 cases.
3. **Informal spend verbs** (§3.2) — training-data fix.
4. **"Analyze" → ANALYSIS** (§3.6) — cue-coverage fix, pattern well understood.
5. **SUMMARY/INSIGHTS/ANALYSIS boundary** (§3.7) — needs a product decision.
6. **Span swallowing** (§3.1) and **hallucinated category** (§3.5) — trace both.

Every item above should become a QA case in `qa_scenarios.jsonl` regardless of
whether it is fixed immediately, so it can never silently regress.
